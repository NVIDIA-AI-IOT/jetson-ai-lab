[Voice AI Workbench](https://github.com/NVIDIA-AI-IOT/multi_modal_ai_studio), formerly **Multi-modal AI Studio (MMAS)**, helps developers give a robot a voice and a character. Compare independent ASR, LLM/VLM, and TTS services through standard APIs, tune the LLM's system prompt, and inspect recorded transcripts, latency, barge-in, audio playback, and device utilization. Optional vision input remains supported. The GitHub repository and existing session formats retain their original names; the recommended package and CLI name is now `voice-ai-workbench`.

The recommended quick start runs on **Jetson Orin Nano, Jetson AGX Orin, and Jetson AGX Thor** without requiring an NGC entitlement or a Riva installation. It combines Faster-Whisper and Kokoro through Speaches with a text-only Gemma 4 E2B LLM. The original Riva and Cosmos-Reason2 voice-and-vision configuration remains available below as an advanced Thor workflow.

<Note title="Application and backend versions">
  [Voice AI Workbench 0.2.0](https://github.com/NVIDIA-AI-IOT/multi_modal_ai_studio/releases/tag/v0.2.0) is available on [PyPI](https://pypi.org/project/voice-ai-workbench/0.2.0/). The GitHub release provides artifacts, checksums, and limitations. The independently versioned Speaches backend remains pinned to 0.9.0-rc.3; the workbench release does not make that backend a GA release. Use the REST quick start for initial evaluation.
</Note>

## Recommended Quick Start: Orin Nano to Thor

The starter pipeline is entirely local:

```text
browser microphone
  -> Speaches Faster-Whisper (:18080)
  -> Gemma 4 E2B llama.cpp (:8080)
  -> Speaches Kokoro (:18080)
  -> browser speaker
```

Speaches exposes OpenAI-compatible speech APIs. Gemma is a separate OpenAI-compatible Chat Completions service, so you can replace the LLM without restarting speech.

### Requirements

- A Jetson Orin or Thor running a Jetson Linux release whose driver supports CUDA 13 containers
- Docker with the NVIDIA container runtime
- A Chromium-based browser on the Jetson or another computer on the same trusted network
- Enough free storage for the two container images and model cache

<Warning title="Orin Nano memory headroom">
  On an 8 GB Orin Nano, stop unrelated GPU workloads before starting the pipeline. A 16 GB swap file is strongly recommended to absorb transient CPU-side allocations while the models load. Swap does not increase GPU memory; the default tiny ASR model, 2048-token Gemma context, and text-only `--no-mmproj` configuration keep the active pipeline small enough for this device.
</Warning>

### 1. Install Voice AI Workbench

Install the published application in an isolated Python 3.11+ environment. Clone the matching release only for the backend launcher scripts; the installed wheel supplies the Web UI and built-in presets.

```bash
python3 -m venv ~/voice-workbench-venv
source ~/voice-workbench-venv/bin/activate
python -m pip install voice-ai-workbench==0.2.0
voice-ai-workbench --version

git clone --branch v0.2.0 --depth 1 \
  https://github.com/NVIDIA-AI-IOT/multi_modal_ai_studio.git \
  ~/voice-workbench-backends
cd ~/voice-workbench-backends
```

The commands below run the backend scripts from `~/voice-workbench-backends`. The application is launched from outside that checkout so Python uses the installed wheel rather than importing source files from the current directory.

If creating the environment fails because `ensurepip` is missing, install your OS's matching venv package, such as `sudo apt install python3-venv`. Browser audio does not require the optional PyAudio package. Keep earlier `multi-modal-ai-studio` installations in a separate environment; see the [upgrade instructions](https://github.com/NVIDIA-AI-IOT/multi_modal_ai_studio/blob/main/docs/development/releasing.md#upgrading-an-earlier-mmas-installation) before reusing one.

### 2. Start and verify speech

```bash
./scripts/speaches_speech.sh doctor
./scripts/speaches_speech.sh start
./scripts/speaches_speech.sh verify
```

The launcher pulls the pinned dual-architecture CUDA image and installs these starter models in a persistent Docker volume:

<div style="overflow-x: auto;">

| Stage | Model |
| --- | --- |
| ASR | `Systran/faster-whisper-tiny.en` |
| TTS | `speaches-ai/Kokoro-82M-v1.0-ONNX-fp16` |
| Default voice | `af_heart` |

</div>

`verify` synthesizes a short sample through the TTS API and transcribes it through the ASR API. Do not continue until it prints `Speech API smoke test passed`.

### 3. Start and verify Gemma 4

```bash
./scripts/gemma4_llm.sh doctor
./scripts/gemma4_llm.sh start
./scripts/gemma4_llm.sh verify
```

The launcher selects the Jetson Orin or Thor llama.cpp image automatically and serves `unsloth/gemma-4-E2B-it-GGUF:Q4_K_S`. It enables Gemma's MTP draft, disables hidden reasoning for lower time to first speech, limits context to 2048 tokens, and skips the multimodal projector because this starter configuration uses Gemma as a text LLM.

### 4. Start the workbench

```bash
cd ~
voice-ai-workbench --preset speaches-jetson --port 8092
```

Open the URL printed by the server, normally:

```text
https://<JETSON_IP>:8092
```

After verifying that the address belongs to your Jetson on a trusted network, accept its local development certificate, allow microphone access, select **Check servers**, and start a session. Try these short prompts:

```text
Hi, can you hear me?
What is one plus one?
Tell me one short safety rule for a home robot.
```

While the assistant is speaking, test interruption with:

```text
Stop. What is one plus one?
```

When you stop the session, select it in the left sidebar to review the transcript, audio waveforms, pipeline timeline, time-to-first-audio measurements, and Jetson system information.

![Voice AI Workbench showing a recorded NVIDIA Speech conversation, audio waveforms, and latency timeline on Jetson Thor](/images/tutorials/voice-ai-workbench-nvidia-speech.png)

This recorded session uses **Nemotron 3.5 ASR → Gemma 4 E2B → Magpie TTS** with the NVIDIA Speech — Realtime preset, an alternative to the Speaches quick start. It illustrates the shared review interface, not a controlled performance benchmark; the internal hostname and IP addresses are omitted.

### From a browser test to a robot's audio devices

Start with the **Browser / WebRTC** microphone and speaker selections in the **Devices** tab. They use the computer that opened the page, while model inference runs on Jetson. This is the simplest way to compare models, adjust the system prompt, and measure responsiveness without attaching audio hardware to the robot.

Once the conversation works, connect a USB microphone and speaker to Jetson and select the **Server USB** devices instead. Save a separate preset with those device choices so the robot uses its own audio hardware, not the laptop's. Recheck capture, playback, and barge-in: acoustic echo, device sample rates, and microphone levels differ between the two paths. A speakerphone with acoustic echo cancellation or a headset is useful during testing.

The CLI also offers experimental headless operation using a saved configuration. See the [device and headless setup instructions](https://github.com/NVIDIA-AI-IOT/multi_modal_ai_studio/blob/main/INSTALL.md) before deploying without a browser; a successful browser test alone does not qualify the server-local device path.

### REST and Realtime speech paths

The default `speaches-jetson` preset uses REST transcription and speech APIs. The workbench detects speech boundaries locally and sends each completed utterance as a WAV request. Its Realtime ASR adapter instead sends microphone audio over a WebSocket and consumes the backend's speech-boundary and transcription events. Realtime ASR does not require Realtime TTS; the Speaches Realtime ASR preset keeps Kokoro on the REST speech API.

<Warning title="Speaches Realtime evaluation">
  Concurrent ASR, LLM, and TTS testing on Orin Nano exposed errors and delayed interruption with the pinned public Speaches 0.9.0-rc.3 image. Follow-up tests passed with a locally corrected backend, but that corrected image is not yet published. Updating Voice AI Workbench alone does not install those server fixes. Keep the REST preset for the recommended public quick start; the Realtime command below is an optional diagnostic path, not equivalent qualification of the public image.
</Warning>

To evaluate the Realtime ASR path against a suitable backend, stop the current workbench process with **Ctrl+C** in its terminal, then restart it with the alternate preset. Keep the model services running:

```bash
cd ~
voice-ai-workbench --preset speaches-realtime-asr-jetson --port 8092
```

Speaches emits Realtime session and speech-boundary events, then transcribes each completed speech segment with Faster-Whisper. This is not token-by-token model-native Faster-Whisper decoding, so partial transcript deltas may not be available.

### Try NVIDIA open speech models

The repository also includes reference services for Nemotron 3.5 ASR and Magpie TTS. They expose REST and WebSocket Realtime adapters while keeping Gemma or another independently served LLM. The launcher manages speech only, not the LLM:

```bash
cd ~/voice-workbench-backends
./scripts/nvidia_open_models_speech.sh build
./scripts/nvidia_open_models_speech.sh start
./scripts/nvidia_open_models_speech.sh verify
cd ~
```

See the [NVIDIA open speech model setup](https://github.com/NVIDIA-AI-IOT/multi_modal_ai_studio/blob/main/docs/setup_open_models_jetson.md) for model access, presets, and platform notes.

For the complete Speaches lifecycle, model overrides, API endpoints, and troubleshooting, see the [Speaches on Jetson guide](https://github.com/NVIDIA-AI-IOT/multi_modal_ai_studio/blob/main/docs/setup_speaches_jetson.md).

## Go further on Thor: richer speech and vision

Thor's additional memory makes it a useful platform for exploring larger models, but a larger model is not automatically a more responsive voice assistant. Keep the quick start as a baseline, change one service at a time, and compare recognition accuracy, time to first text, time to first audio, and playback gaps with the same input.

### Explore a multilingual ASR model

The quick start's `tiny.en` model is English-only. Download the multilingual small model into the same Speaches service, then reload the ASR model list and select it in **Configuration → ASR**:

```bash
curl --fail --show-error -X POST \
  'http://localhost:18080/v1/models/Systran%2Ffaster-whisper-small'
```

Use the language corresponding to the input speech. A larger Faster-Whisper variant, such as `large-v3-turbo`, is a further comparison candidate, not a latency improvement guaranteed by the workbench. Speaches and Faster-Whisper still determine whether recognition is segment-based or produces partial transcripts; changing the model size or using a WebSocket does not itself make decoding incremental.

### Add a larger LLM or visual context

[Gemma 4 12B](/models/gemma4-12b/) is a candidate for a richer conversational and visual assistant. Start with reasoning disabled and short answers, then compare it with E2B using identical prompts. Do not infer speed from parameter count alone or compare different thinking settings and response lengths as if they were equivalent.

Gemma's image understanding is **VLM**, not a robot **VLA** action policy. Its text output does not directly implement robot motion control. The quick start launcher deliberately uses `--no-mmproj` and disables vision. To test a camera, the serving configuration must support image input, and **Configuration → LLM / VLM** must enable vision. Select a browser camera under **Devices**, start with one small frame per turn, and verify the answer changes with the image. See the [vision setup guide](https://github.com/NVIDIA-AI-IOT/multi_modal_ai_studio/blob/v0.2.0/docs/vlm_guide.md).

<Tip title="Thor evaluation settings">
  A standalone check on Thor with Gemma 4 12B QAT Q4_0 used its matching multimodal projector, 4096-token context, one request slot, `--reasoning off`, `--fit off`, and `--load-mode mmap`. It correctly identified a red circle and blue square through the released workbench's image-request adapter. This verifies an image request, not camera capture, video understanding, or a robot action policy. Automatic memory fitting did not reach ready in that evaluation; inspect server logs instead of assuming the application is at fault.
</Tip>

### Compare Qwen3-TTS with Kokoro or Magpie

[Qwen3-TTS 1.7B CustomVoice](https://huggingface.co/Qwen/Qwen3-TTS-12Hz-1.7B-CustomVoice) is a further Thor evaluation option. Serve it with an OpenAI-compatible speech endpoint, such as the [vLLM-Omni Qwen3-TTS deployment](https://docs.vllm.ai/projects/vllm-omni/en/latest/), then select **OpenAI REST API** in the workbench's TTS tab and set the endpoint, model, and a supported voice such as `ryan`. Begin with **Start speaking before LLM finishes** off, then test overlapping generation separately.

Keep the ASR, LLM, and TTS endpoints independent: for example, compare **Faster-Whisper small → Gemma 4 12B → Qwen3-TTS** with **Nemotron 3.5 ASR → Gemma → Magpie**. Test the combined load, interruption, and recovery rather than assuming three successful standalone requests qualify the complete robot pipeline. Model-native audio streaming also depends on the serving API and the request fields; a PCM response alone does not prove incremental model generation.

In the evaluated vLLM-Omni configuration, an explicit streaming request returned its first PCM bytes before synthesis finished. The released 0.2.0 generic REST TTS adapter does not send that provider-specific `stream` field, and the same server buffered that request until completion. Do not present the model's streaming timing as the released application's time to first audio.

<Note title="Released features and follow-up work">
  This tutorial uses Voice AI Workbench 0.2.0. Dedicated Qwen3-TTS instructions, VoiceDesign, and reference-voice cloning controls are separate 0.3.0 development work, not prerequisites for this release or capabilities implied by selecting a CustomVoice model.
</Note>

### Advanced architecture

Voice AI Workbench does not run the AI models by itself. It connects to model services through standard APIs, which makes the pipeline easy to swap and tune.

![Multi-Modal AI Studio architecture](https://raw.githubusercontent.com/NVIDIA-AI-IOT/multi_modal_ai_studio/main/docs/images/MMAS-arch.png)

### Step 1: Start NVIDIA RIVA SDK (ASR + TTS)

RIVA provides the ASR and TTS services for the voice pipeline. This tutorial uses **Riva 2.24.0 Embedded (aarch64)**; see the [Riva support matrix](https://docs.nvidia.com/deeplearning/riva/user-guide/docs/support-matrix/support-matrix.html) for platform and model compatibility.

Before running the commands below, install and initialize RIVA by following the [NVIDIA Riva setup for voice ASR/TTS](https://github.com/NVIDIA-AI-IOT/multi_modal_ai_studio/blob/main/INSTALL.md#nvidia-riva-setup-for-voice-asrtts) instructions in the application repository.

After RIVA is installed and initialized, start it from the RIVA quick start directory:

```bash
cd riva_quickstart_arm64_v2.24.0
bash riva_start.sh
```

Wait for the server to be ready. You can monitor the logs:

```bash
docker logs -f riva-speech
```

Look for:

```text
RIVA server listening on 0.0.0.0:50051
All models loaded successfully
```

This can take several minutes, especially the first time after boot.

### Step 2: Start vLLM with Cosmos-Reason2

Next, start the LLM/VLM backend. RIVA uses ports `8000`, `8001`, and `8002`, so this tutorial serves vLLM on **port 8010**.

Use the [Cosmos Reason2 8B model page](/models/cosmos-reason2-8b/) for the latest serving commands, including NGC CLI setup if you have not configured it yet. The vLLM path uses the FP8 checkpoint from NGC, so download the model first and set `MODEL_PATH`:

```bash
ngc registry model download-version "nim/nvidia/cosmos-reason2-8b:1208-fp8-static-kv8" \
  --dest ~/.cache/huggingface/hub

export MODEL_PATH="${HOME}/.cache/huggingface/hub/cosmos-reason2-8b_v1208-fp8-static-kv8"
```

Then serve the model on port `8010`:

```bash
mkdir -p ~/.cache/vllm

sudo docker run -it --rm --runtime=nvidia --network host \
  -v $MODEL_PATH:/models/cosmos-reason2-8b:ro \
  -v ${HOME}/.cache/vllm:/root/.cache/vllm \
  ghcr.io/nvidia-ai-iot/vllm:0.14.0-r38.3-arm64-sbsa-cu130-24.04 \
  vllm serve /models/cosmos-reason2-8b \
    --served-model-name nvidia/cosmos-reason2-8b-fp8 \
    --max-model-len 8192 \
    --gpu-memory-utilization 0.7 \
    --reasoning-parser qwen3 \
    --media-io-kwargs '{"video": {"num_frames": -1}}' \
    --enable-prefix-caching \
    --port 8010
```

Wait until the server is ready:

```text
INFO:     Uvicorn running on http://0.0.0.0:8010
```

Verify the OpenAI-compatible API:

```bash
curl http://localhost:8010/v1/models
```

You should see `nvidia/cosmos-reason2-8b-fp8` in the response.

<Warning title="⚠️ Port conflict with RIVA">
  Do not use vLLM's default port when RIVA is running. Keep vLLM on `8010` or another unused port, then use the same port in the workbench's LLM API base URL.
</Warning>

### Step 3: Start Voice AI Workbench

In a **new terminal**, keep RIVA and vLLM running, then activate the application environment created in the quick start. If you skipped that section, first complete its installation step.

```bash
source ~/voice-workbench-venv/bin/activate
cd ~
```

Launch the Studio server and point it at the local RIVA and vLLM services:

```bash
voice-ai-workbench --port 8092 \
  --asr-scheme riva --tts-scheme riva \
  --asr-server localhost:50051 \
  --tts-server localhost:50051 \
  --llm-api-base http://localhost:8010/v1 \
  --llm-model nvidia/cosmos-reason2-8b-fp8
```

### Step 4: Open the Web Interface

From your client PC browser, open:

```text
https://<JETSON_IP>:8092
```

Verify that this is your Jetson's address on a trusted network before accepting its self-signed development certificate. HTTPS is required because browsers restrict microphone and camera access on insecure origins.

When prompted, allow microphone and camera permissions.

<Note title="📝 Why these settings?">
  - **Streaming Responses** delivers LLM text incrementally. With **Start speaking before LLM finishes** enabled in the TTS tab, the workbench can send text chunks to TTS before the response is complete.
  - **Conversation History** gives the LLM context from previous turns, enabling follow-up questions.
  - **Vision (Video Input)** captures frames from the camera and includes them in the LLM prompt.
  - **System Prompt** shapes the AI's behavior. Shorter responses mean faster TTS and a more conversational feel.
</Note>

## Troubleshooting

<details>
<summary>Speaches reports <code>No models found</code></summary>

Confirm the service and installed models, then rerun the idempotent start command if either starter model is missing:

```bash
cd ~/voice-workbench-backends
./scripts/speaches_speech.sh status
./scripts/speaches_speech.sh models
./scripts/speaches_speech.sh start
```

</details>

<details>
<summary>Gemma or Kokoro fails to load on an 8 GB Orin Nano</summary>

Stop unrelated GPU containers, keep the default tiny ASR model and 2048-token Gemma context, and confirm that swap is active:

```bash
docker ps
free -h
swapon --show
```

The recommended configuration was qualified with a 16 GB swap file. Swap helps with transient CPU allocations during loading, but it does not increase GPU memory. If memory pressure continues, use a smaller OpenAI-compatible LLM while keeping the same speech service.

</details>

<details>
<summary><code>voice-ai-workbench: command not found</code></summary>

Activate the Python virtual environment before launching:

```bash
source ~/voice-workbench-venv/bin/activate
voice-ai-workbench --help
```

</details>

<details>
<summary>Port <code>8092</code> is already in use</summary>

Identify the listener before stopping anything:

```bash
ss -ltnp 'sport = :8092'
```

If it is your existing workbench process, stop it with **Ctrl+C** in its terminal. Otherwise, leave that service running and choose another port, for example `voice-ai-workbench --preset speaches-jetson --port 8101`, from outside the backend checkout.

</details>

<details>
<summary>vLLM fails to start because ports are busy</summary>

Do not use vLLM's default port when RIVA is running. Use `--port 8010` or another unused port, then update the Studio LLM API base URL to match.

</details>

<details>
<summary>Browser cannot access the microphone or camera</summary>

Make sure you opened the HTTPS URL:

```text
https://<JETSON_IP>:8092
```

Verify the Jetson address before accepting its self-signed development certificate, then allow browser permissions for microphone and camera.

</details>

<details>
<summary>ASR does not resume after being muted for a long time</summary>

The ASR stream can time out if it stops receiving audio for an extended period. Stop the session with the red button, then start a fresh session.

</details>

<details>
<summary>GPU memory is not released after stopping vLLM</summary>

Check whether another model process or container is still running:

```bash
docker ps
free -h
```

Stop only the model services you no longer need. Linux page-cache reclamation does not release memory held by a live inference process; do not use `vm.drop_caches` as a GPU-memory fix.

</details>
